## 4. 数据特征

### 4.1 会话结构

#### 单轮对话 (~63%)
```
question: 玩家初始问题
answer:   客服单条回复
```

#### 多轮对话 (~37%)
多轮对话存储在 `answer` 字段中，格式为**最新的回复在前**（逆时序）:

```
answer 字段结构:
├── [最新 CS 回复]      ← 纯文本，无引用符号
├── [> 引用的原始问题]   ← 以 > 开头的引用行
├── [玩家追加消息]      ← 纯文本
├── [时间戳分隔符]      ← 如 "2024年3月13日(水) 12:38 【ぽちゃガチョ！カスタマーサポート】"
├── [> 引用的历史回复]   ← 被引用的旧回复
└── [原始 CS 回复]      ← 最早的客服回复
```

**典型 2 轮对话示例**:
```
いつも「ぽちゃガチョ！」をご利用いただき... (CS Reply 2 - 最新)
> 前回の問い合わせ内容... (引用)
了解しました。端末の情報を教えてください。 (玩家追加消息)
2024年3月13日(水) 12:38 【ぽちゃガチョ！カスタマーサポート】: (时间戳分隔)
> いつも「ぽちゃガチョ！」を... (CS Reply 1 - 被引用)
> ゲームがクラッシュします (原始问题)
いつも「ぽちゃガチョ！」を... (CS Reply 1 - 纯文本重复)
```

### 4.2 多轮对话解析规则

#### 解析算法 (`parse_thread_turns`)
1. **行分类**: 按前缀将每行分类为
   - `quoted`: 以 `>` 开头的引用行
   - `timestamp`: 匹配正则 `\d{4}年\d{1,2}月\d{1,2}日[（(][月火水木金土日][）)]\s+\d{1,2}:\d{2}`
   - `plain`: 纯文本行

2. **提取纯文本段落**: 只保留 `plain` 类型的连续段落

3. **角色识别**: 使用 `CS_OPENER_REGEX` 识别客服回复
   - 匹配开头: `いつもご利用` / `ご連絡` / `平素より` / `お世話になっております`
   - 匹配 → CS 回复; 不匹配 → 玩家追加消息

4. **配对规则**:
   - CS 回复 + 玩家消息 → 组成一轮
   - CS 回复 + CS 回复 → 单轮（无追问）
   - 最后只保留最多 2 轮（按时间顺序 老→新）

### 4.3 字段说明
| 字段名 | 说明 |
|--------|------|
| mail_id | 原始邮件ID |
| question | 用户提问内容（初始问题） |
| answer | 客服回复内容（单轮）或多轮对话完整线程 |
| inquiry_type | 自动提取的问题类型 |

### 4.4 多轮对话类型分布

| 场景类型 | 占比(估) | 特征 |
|----------|----------|------|
| **信息收集** | ~40% | CS 要求补充信息 → 玩家提供 → CS 处理 |
| **排障升级** | ~30% | CS 给方案 → 玩家说无效 → CS 给更深方案 |
| **纠正补充** | ~15% | 玩家追加/更正自己的描述 |
| **确认验证** | ~15% | CS 操作后让玩家确认是否解决 |

### 4.5 异常值处理

#### 清洗阶段已处理的异常
| 异常类型 | 处理方式 | 说明 |
|----------|----------|------|
| 无客服回复 | 删除整条 | `answer` 为空或只含引用 |
| 自动回复 | 删除 | 系统生成的标准确认邮件 |
| 格式错乱 | 正则清洗 | 去除 `※本メール...` 签名、日期戳分隔符 |

#### 解析阶段的异常处理
| 异常类型 | 处理策略 |
|----------|----------|
| 无法识别 CS 回复 | 跳过该样本（返回空列表） |
| 超过 2 轮 | 只保留最近 2 轮 |
| 时间戳格式不一致 | 使用模糊匹配，不匹配则视为 plain |
| 混合语言内容 | 保留原样，由 embedding 模型处理 |

## 5. 评估指标说明

### 5.1 自动评估指标

| 指标 | 计算方法 | 评分范围 | 说明 |
|------|----------|----------|------|
| **Rouge-1 F1** | fugashi 日语分词后计算 unigram 重叠 | 0-1 | 关注关键词匹配 |
| **BLEU** | sacrebleu char-level (日语不分词) | 0-1 | 关注语法流畅度 |
| **语义相似度** | bge-m3 cosine similarity | 0-1 | 跨语言语义匹配 |

### 5.2 颜色标记规范 (HTML 报告)

| 颜色 | 分数范围 | 含义 |
|------|----------|------|
| 🟢 绿色 | ≥0.7 | 高质量回复 |
| 🟡 黄色 | 0.4-0.7 | 中等质量，需检查 |
| 🔴 红色 | <0.4 | 低质量，需人工介入 |

### 5.3 多轮对话评估策略

- **每轮独立评分**: 每轮对话分别计算 Rouge/BLEU/语义相似度
- **样本平均分**: 多轮样本的最终得分为各轮平均分
- **上下文传递**: 评估脚本通过 FastAPI session 保持对话状态，模拟真实交互

## 6. 使用建议

### 6.1 训练阶段
- 使用 `train.csv` 构建向量索引 (FAISS)
- 对多轮对话进行拆分入库：每轮作为独立 QA 对
- question 字段用于检索，answer 字段用于生成参考

### 6.2 评估阶段
- 使用 `eval.csv` 进行端到端评估
- 运行 `codes/evaluation/run_eval.py` 生成报告
- 检查 HTML 报告中的低分样本（红色标记）
- 查看大模型质量评估总结获取改进建议

### 6.3 注意事项
1. **数据倾斜**: 57% 为故障报告，需注意其他类型的召回率
2. **多轮占比**: 37% 为多轮，评估时必须考虑对话历史
3. **语言特性**: 日语敬语变化丰富，BLEU 可能偏低属正常
4. **延迟考量**: API 调用延迟约 2-5s/轮，评估 40 条约需 5-10 分钟
